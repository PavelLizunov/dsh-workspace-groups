# Spec: GitHub stable/latest для операторских DSH-плагинов (v4, на техническое ревью)

## 1. Intent & Invariants
- Для каждого утверждённого оператором плагина отдельный GitHub repo: множество `vX.Y.Z-rc.N` pre-release и один указатель `latest` на последний проверенный immutable stable `vX.Y.Z`. Продуктивный `web-015` использует только verified stable архив, закреплённый в `package.json` + frozen lockfile; выход нового `latest` сам ничего не устанавливает.
- `github-release-inventory.json` (schema `github-release-inventory.schema.json`) описывает 14 ordered bundles и 20 direct dependencies; captured_at, DSH/pnpm versions, SHA256 manifest/lockfile/workspace/patch, `source_commit` full SHA или null, `source_dirty`, `direct_dependency`, `declares_dsh_bundle`, sorted file-tree hash. Перед любой staging-мутaцией переснять inventory и сравнить все четыре SHA с live, иначе abort. Не путать это с человеческим утверждением ownership/license.
- Из channel исключены два DSH core, third-party без отдельного одобренного fork и binary-only TTS/mobile до формальной source recovery. Действующие локальные `.local.*` — rollback baselines, а не stable GitHub releases. Приватный `ai-gateway` не публикуется целиком; выделение `dsh-cpamc-limits` в отдельный private repo — отдельный пользовательский выбор, не действие этого плана. У `dsh-workspace-groups`, Fleet Cleaner и limits есть грязные/неполные release gates, stable выпуск пока запрещён.
- Релиз подписан доверенным для репозитория операторским tag key, имеет зафиксированный source→build provenance и immutable uploaded `.tgz`. `latest` — consistency pointer, max verified SemVer — authority; при расхождении fail closed. Любое изменение GitHub settings, Git history, visibility, repo, Release, DSH или рестарт требует отдельного решения пользователя.

## 2. Interface / Data Contract
```text
Eligible = enabled && operator-controlled/approved fork && source/ownership/license
  verified && clean source && reproducible tested packed artifact.
Stable: package.version=X.Y.Z; annotated signed tag=vX.Y.Z;
  GitHub draft=false, prerelease=false, immutable=true, asset=name-X.Y.Z.tgz.
Prerelease: X.Y.Z-rc.N; prerelease=true; never production.
Discovery: paginate releases -> strict stable SemVer -> verify tag/commit,
  immutable, build provenance, release attestation and asset -> max SemVer;
  require /releases/latest == selected; mismatch/older/equal-different -> abort.
```
- **Signed tag trust root**: per-repo policy stores signer scheme+GPG fingerprint OR SSH principal+trusted public-key fingerprint, approved GitHub account and allowed build signer/workflow identity (no secret key material). `git tag -v`/`verify-tag --raw`, peel tag to full source commit and compare allowlist; GitHub `Verified` alone insufficient. Rotation, revocation and policy changes require operator decision; old releases retain their historical trust policy.
- **Build provenance (separate from release attestation)**: choose and document per-repo mode BEFORE stable. A: trusted GitHub Actions fresh checkout of peeled commit on pinned Node/pnpm/frozen lockfile, tests/build/pack; action dependencies pinned by full SHA; verified build attestation subject matches `.tgz` and contains repo, tag/ref, SHA, signer workflow/builder identity. B (if private attestation unavailable): independent clean builds by two operator-approved builders from same signed tag/pinned toolchain, identical canonical unpacked-tree SHA, signed provenance by allowlisted operator key. Canonical hash: sort normalized UTF-8 POSIX relative paths; reject duplicates, symlinks, escaping paths and unexpected file types; hash UTF-8 records `relative-path + NUL + SHA256(file bytes) + LF` with SHA-256, include file mode policy separately; no ignored runtime files. Build-mode failure keeps `stable_eligible=false`. Release attestation proves published asset identity, **not** its build provenance.
- **Release order**: commit version → signed annotated tag → detached fresh checkout → build/test/pack and inspect tar inventory/license/secrets → create draft/upload exact `.tgz`+SHA256SUMS+signed provenance → canary download exact draft asset, compare hashes and source → publish with `make_latest=false` → verify `immutable=true`, release attestation and uploaded asset digest/tag SHA → then `PATCH make_latest=true` → paginate all releases and require `/latest == max verified strict SemVer`. If verification fails, do NOT assign latest; failed immutable release is quarantined/ineligible in a signed operator-maintained release policy, and update fails closed while a higher unverified release exists. Metadata `prerelease/latest` remains editable despite immutable asset/tag.
- **Verifier**: current `gh 2.45.0` cannot verify releases; future release pipeline pins a newer tested `gh` binary/version+SHA-256 and mandates `gh release verify TAG --repo OWNER/REPO` and `gh release verify-asset TAG FILE --repo OWNER/REPO`, with captured JSON/command evidence and separate build-provenance verification. No generic SHA-only alternative. Negative fixtures: wrong owner, tag, changed asset, missing/foreign attestation, same filename/new digest, unauthenticated private repo.
- **Private API**: pinned owner/repo + expected visibility, read-only scoped GitHub App credential (fine-grained `Contents:read` temporary fallback), no tokens in URLs/logs/manifests. Authenticated GitHub API initial request; HTTPS 302 to no-userinfo host **without Authorization**; verify downloaded bytes against asset.digest, attestation, checksum and signed provenance. Any 401/403/404/rate limit/network error aborts before local cache or profile mutation. No Git URLs or GitHub autogenerated source tarballs as DSH dependency. Cache no-clobber under `~/.dsh/bundles/<owner>/<repo>/<package>/<version>/<sha>/` then staged frozen lockfile.
- **KeyGuard in limits**: choose **vendored, source-tracked**: include only required KeyGuard modules with their verified MIT license, upstream repo/full source SHA and vendored-tree hash. Fix imports to stay inside package; CI tests clean packed artifact and scans for secrets/private gateway files. Do not use an implicit `../../../keyguard`, floating workspace dependency or binary-only staging vendor fix.
- **DSH anti-resurrection**: six retired direct dependencies declaring `dsh.bundle.patch` are `@deepseek-harness-tui/dsh-tui`, `dsh-better-sidebar`, `dsh-client-ui-session-id`, `dsh-homelab-overview`, `dsh-ouroboros`, `dsh-telegram`; seventh `dsh-jev-supervisor` has no bundle metadata. In an **independently approved** retired-dependency migration, stage removal of all seven direct deps, associated lock edges and patch rows while preserving old tgz/data. Before install assert A: exact ordered `bundle_order`; B: set(direct deps declaring bundle)==set(`bundle_order` minus two core); C: retired ∩ dependencies empty. During every guarded `dsh plugin install`, hold `flock`, snapshot manifest, lockfile, workspace config, profile patch, **whole node_modules incl symlinks**, then postcheck exact bundles+dependency map+lock; on fail restore full snapshot before any further pnpm, alert operator. Without migration, raw `dsh plugin` remains unsafe.
- **Two separate outcomes**: plugin-channel completeness means all enabled operator/fork packages either have verified stable releases or are explicitly gated local baselines; it does **not** imply whole-profile recovery. Full-profile recovery separately pins DSH 0.1.5-rc.2 core, third-party/registry packages, TTS/mobile baselines, profile metadata, patches, local archive cache and special release-specific `@deepseek-ai/dsh-time-context` path (must be eliminated or replicated before standalone disaster-recovery claim). Exact approved DSH version/image is a canary prerequisite.

## 3. Verification Checklist (Definition of Done)
- [ ] `python3 -m json.tool`, JSON Schema validation and **fresh SHA comparison** to live of inventory; 14 bundles, 20 direct deps, six resurrection-capable retired + one plain Jev identified. Signer allowlist, actual owner, visibility and license decisions made **before** stable publishing.
- [ ] For each candidate: strict stable/prerelease SemVer, independently checked build provenance A/B, signed tag, immutable draft flow with `make_latest=false`, verified attestations/assets and finally `/latest` equals max verified stable; negative canary covers transient unverified release and manual latest drift.
- [ ] Canary with exact pinned DSH core verifies bytes installed from downloaded asset, clean Host/Client boot, retired-bundle guard and approved rollback; failure leaves production unchanged. Whole-profile recovery is assessed separately, not promised by plugin channel.
- [ ] GitHub repo creation, settings changes, source push, releases, profile install and service restart all require separate human decisions. GPT Pro OK is technical signoff of this architecture only.
