# Spec: Выкладка локальных плагинов без отката

## 1. Intent & Invariants
- What: локальные плагины профиля `web-015` ставятся как неизменяемые версии, так что `dsh plugin add` и `pnpm install` больше не разворачивают старый tarball поверх свежего кода. Сегодня `package.json` профиля держит `file:…/*.tgz`, а pnpm при любом прогоне заново распаковывает архив. Так 23 сентября пропала цветовая пометка `dsh-workspace-groups`, а 24-го вкладка Limits отдавала сборку от 14 сентября без xAI.
- Invariants:
  - Ни одна выкладка не запускает `pnpm install` по профилю, пока в зависимостях остаётся хотя бы один устаревший `file:…/*.tgz`: это откатывает все такие плагины разом.
  - Выложенная версия неизменяема. Правка исходника не меняет то, что грузит профиль, пока не собрана и не выложена новая версия.
  - Откат — это возврат зависимости на предыдущую версию, а не восстановление из бэкапа.
  - `dsh plugin` остаётся единственной командой установки: он и так передаёт аргументы в pnpm и понимает `link:`.
  - Рестарт `dsh-web` нужен только когда изменилась хостовая часть; клиентский бандл подхватывается по mtime. Каждый рестарт обрывает чаты и требует отдельного согласия.

## 2. Interface / Data Contract
Штатный механизм, без нового кода. Каталог выкладки `/var/lib/dsh/.dsh/packages/<name>/<version>/` — распакованный пакет одной версии. Зависимость профиля:

```json
"dsh-workspace-groups": "link:/var/lib/dsh/.dsh/packages/dsh-workspace-groups/0.1.0-rc1.local.2"
```

`link:` не копирует файлы, поэтому повторный `pnpm install` не может подменить содержимое. Версия в пути — часть контракта: новый релиз получает новый каталог и новую строку зависимости.

Правило выпуска одной версии:
1. Собрать пакет в его репозитории (`pnpm build`).
2. `pnpm pack` в каталог артефактов, имя файла содержит версию.
3. Распаковать в новый каталог `/var/lib/dsh/.dsh/packages/<name>/<version>/`.
4. Сверить sha256 распакованного `lib/client.js` с собранным.
5. Поменять одну строку зависимости на `link:` и запустить `dsh plugin --profile web-015 install` только когда все остальные `file:…/*.tgz` уже переведены или отсутствуют.

Первая партия: `dsh-workspace-groups` (сборка с цветом, коммит `8718d7f`), `dsh-client-ui-teratts` (живой TTS-фикс, которого нет в git), `dsh-cpamc-limits` (xAI, коммиты до `f3196a7`). Сейчас профиль смотрит на них вразнобой: groups и teratts — реальные каталоги, распакованные из старых архивов и затем затёртые руками, cpamc — симлинк прямо в репозиторий.

## 3. Verification Checklist (Definition of Done)
- [ ] После `dsh plugin install` `lib/client.js` трёх плагинов совпадает по sha256 с выложенной версией, а не с архивом от 14 сентября.
- [ ] Повторный `dsh plugin install` не меняет ни байта этих файлов.
- [ ] `dsh-workspace-groups` отдаёт граф с цветовой пометкой, `dsh-cpamc-limits` содержит `sidebarRightTabs` и xAI.
- [ ] В `package.json` профиля не осталось `file:` на архив старше выложенной версии для этих трёх.
- [ ] Откат проверен: возврат строки зависимости на прошлую версию возвращает прежний бандл.

Открытые вопросы к ревью:
1. `link:` на каталог версии против `file:` на свежий tgz с новым именем — что реально не откатывается при `pnpm install`, а что pnpm перезапишет?
2. Безопасно ли переводить зависимости по одной, или pnpm при смене одной строки пересоберёт все `file:…/*.tgz`?
3. Где держать каталог версий, чтобы он пережил смену релиза DSH: внутри профиля или в `~/.dsh/packages`, как уже лежит `dsh-review`?
